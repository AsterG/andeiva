# Experimental offline boot bundle

Status: development increment, not a signed `.sgu` update or production installer. Debian packages are resolved in a Debian 13 development environment against a privately supplied target dpkg status. The target status, source paths, hostname, addresses and development logs must never enter the bundle.

The builder uses fixed official Debian HTTPS repositories and the installed Debian archive trust keyring. APT signature, expiry and TLS verification remain enabled. The bundle retains public signed release metadata, package indexes, exact package inventory and SHA-256 checksums. Product checksums require an independently trusted/reviewed source; checksums are not signatures or authorization to install.

The local installer accepts only a root-owned bundle under `/var/lib/andeiva-boot-bundles/<inventory-sha256>`. It serializes with boot activation, validates the bundle and simulates an offline APT transaction without upgrades or removals. Before installation it backs up boot/configuration/package state. A private mount namespace receives a read-only bind of `update_initramfs=no`; the host policy file is never rewritten. Kernel/initramfs and host-policy hashes are checked afterwards. It does not activate branding, regenerate boot files, reboot, modify SSH/network policy or run online APT.

Initial native scope is Debian 13 AMD64, BIOS, ext4 root with boot, configuration and backups on that filesystem and no foreign dpkg architectures. No device name, GPU driver or hypervisor is prescribed. Unknown layouts are refused; a capability check is not hardware qualification. A recoverable backup and independent recovery rehearsal are operator prerequisites. Package failure/interruption retains a pending journal and backups; this is not automatic package rollback. The installer refuses ambiguous resumption instead of deleting journals or invoking generic repair commands.

Build inputs are reviewed `andeiva-boot-branding` and `andeiva-boot-activation` DEBs with the same experimental version. No maintainer scripts are permitted in those product packages. Debian dependency maintainer scripts remain third-party code; offline provenance and the private policy namespace do not make them generally harmless. The supported closure and native effects require independent review and real Debian tests.

See [design and trust boundaries](DESIGN.md) and the [English](docs/en.md), [Spanish](docs/es.md) and [Portuguese](docs/pt.md) guides. Run `bash packaging/boot-branding/offline/tests/run.sh` for unit/race/vet, shell checks and mocked installer fixtures. The separate `tests/signature-native.sh PUBLIC_DEBIAN_INRELEASE` gate exercises actual sqv with a valid archive signature, altered cleartext and a valid but untrusted signer; its private test key exists only in temporary development storage. The DEV Dockerfile provides certificates and test tools, never an appliance runtime image.

Completed fixture tests do not qualify native installation, namespace isolation, power-loss recovery or resource usage. These remain independent release-blocking evidence and review gates. No native installation success is claimed by this document.
