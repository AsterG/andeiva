# Offline boot bundle trust and interruption boundaries

This is an experimental internal development procedure. It is not the signed appliance update format, an A/B updater, automatic rollback, a public download or authorization to redistribute Debian binaries. Product DEBs must come from an independently trusted, reviewed build. Their checksums and the bundle checksum establish integrity against that trusted expectation; they do not authenticate a publisher.

## Existing verifier, no trust bootstrap download

Minimal Debian 13 uses `sqv`; the qualified baseline does not include `gpgv`. The verifier reuses the existing `/usr/bin/sqv` and `/usr/share/keyrings/debian-archive-keyring.pgp`. It never trusts a bundle-provided archive keyring or installs a verifier before verifying the bundle. The fixed `.pgp` file is the installed Debian 13 trust anchor; its conventional `.gpg` symlink alias is not consulted. No bundle or caller can select a different keyring. The installer rejects links at the `.pgp` path or its ancestors, non-regular keyrings, non-root ownership and group/world-writable permissions. Absence or failure of the existing verifier is a refusal condition.

The fixed invocation is `sqv --keyring /usr/share/keyrings/debian-archive-keyring.pgp --output PRIVATE_NEW_FILE --cleartext /proc/self/fd/3`. The input is an already opened, bounded public InRelease file. The output is a new file in a private mode-0700 temporary directory; sqv refuses an existing output. Certificate IDs on stdout are not authenticated release text. Only a zero process status allows reading the bounded output file. Processes have a 30-second deadline, bounded stdout, discarded stderr, a clean environment and no shell. Cryptographic policy, key validity, expiry and revocation use the existing verifier defaults; no historical policy or time override is passed. Release date/validity and authenticated index/package hashes are checked separately. A trustworthy local clock and current trusted keyring remain prerequisites.

Debian's installed `/usr/share/doc/sqv/copyright` identifies upstream `sequoia-sqv`, source <https://gitlab.com/sequoia-pgp/sequoia-sqv>, under LGPL-2.0-or-later. The existing verifier is invoked as a separate process, not linked into ANDEIVA. The bundle includes own LICENSE/NOTICE and the Go toolchain LICENSE for the static standard-library helper. Dependency DEBs retain their original copyright files. Independent license review is required before any distribution beyond authorized internal development.

Main `trixie` Release legitimately omits Valid-Until. Its date is checked against future clock skew, but this increment does not invent an expiry or claim bounded main-repository freshness. Fresh DEV resolution, operator review and a trusted clock/keyring remain mandatory; a customer release needs an independently approved freshness policy. Security and updates suites require Valid-Until, reject expired releases and reject Date after Valid-Until.

## Resolver and payload

A nonroot Debian 13 development resolver reads privately supplied target dpkg status and uses fixed official HTTPS repositories with APT signature, date, expiry and certificate validation. A private APT configuration excludes host configuration fragments and sources. Only public signed release metadata, authenticated package indexes, reviewed product packages, resolved dependency packages, fixed scripts/helper/guides and checksums enter the closed inventory. The target status and logs remain temporary private inputs. Each product package has closed control fields and no maintainer scripts/triggers. The activation package must carry `X-Andeiva-Offline-Install-Guard: 1`; that declaration is an input qualification gate, not binary analysis or a signature.

The exact closure depends on the supplied status and repository snapshot. Reproducibility requires the same resolved packages, metadata, source epoch, source and Go toolchain. A later online metadata refresh can produce a different bundle. The DEV container alone installs HTTPS certificates from Debian; the appliance never performs online APT.

### Narrow boot dependency qualification

This increment is not an OS or bootloader updater. Before dependency resolution in DEV and before any runtime early return or APT, the target must already have configured `grub-common`, `grub2-common`, `grub-pc` and `grub-pc-bin` version `2.12-9+deb13u2` (amd64), plus `initramfs-tools` and `initramfs-tools-core` version `0.148.4` (all). Missing, different-architecture/version, duplicate or unconfigured baseline entries are refused. A post-install hash check cannot undo an MBR write, so these packages must never enter the installation closure.

A single compiled profile, sourced from the reviewed public Debian inventory, permits only subsets of 26 exact dependency name/version/architecture/SHA-256 tuples plus the two known product packages. A valid Debian signature alone cannot admit an extra kernel, bootloader, network service, daemon, changed version or changed hash. There is no environment, command-line or bundle override of this profile. Its source is `check/profile.go`; no private target status enters it or the bundle. New component/security versions require a timely reviewed profile update and new qualification; this restriction is not approval to freeze security updates indefinitely or bypass their review.

Runtime archives are copied under APT's canonical cache filenames and rehashed before use. `pkgAcqArchive` in APT 3.0.4 derives these names with `QuoteString`; epoch `:` is encoded as lowercase `%3a`. The bundle retains its numbered, closed inventory paths. Both simulation and installation use absolute paths to the verified canonical cache copies. Without those copies, `--no-download` can fail on local numbered DEBs; this is not fixed by enabling downloads or weakening verification.

## Draft identity decision

The draft bundle ID is SHA-256 of the canonical `SHA256SUMS` bytes. That sorted, closed inventory binds every payload file, including scripts, the checker, documentation, product packages and public provenance. The package-only `manifest.tsv` hash was insufficient: a changed executable could otherwise reuse the same installation/backup directory. Old development artifacts using that ID are obsolete; there is no fallback acceptance of old IDs. Operators must independently trust the expected archive checksum/ID before root execution; a self-consistent inventory is not publisher authentication.

## Local transaction boundaries

The runtime accepts a root-owned bundle at one fixed location derived from the SHA-256 of its canonical checksum inventory. It refuses foreign architectures and unqualified filesystem/firmware layouts. It obtains the same boot-activation lock plus an installer lock. An existing activation binary must report the root-local capability `offline_install_guard: 1`; older binaries require a separate reviewed upgrade. Fresh absence is permitted because the reviewed bundle introduces the guarded binary while a durable marker is already present.

`inspect` uses disposable staging. `install --recovery-verified` preserves pre-install boot/configuration/package backups and creates the global root-0600 `/var/backups/andeiva-boot-offline/install-pending` marker, synchronizing file and directory before APT. This marker supplements process locks: an orphan APT/dpkg child can outlive the installer. Failure never clears it. New installations and guarded activation mutations must refuse it. Status/capability inspection remains separate.

APT uses a new root-0600 `APT_CONFIG`, excluding host apt.conf, fragments, preferences, source lists and hooks. Only explicit local DEBs are passed with no-download/no-upgrade/no-remove. Dependency maintainer scripts are still third-party privileged code. Inside a private mount namespace, the existing initramfs policy is overlaid read-only with `update_initramfs=no`; no host policy is rewritten. The namespace does not alter network interfaces, routes, SSH, drivers or the running kernel. Boot hashes, kernel inventory, original policy, dpkg health, installed versions and the new guard capability must all match postconditions before the marker can be removed durably.

Both simulation and installation capture merged stdout/stderr through a bounded Go logger. Logs are created exclusively as root-0600 files and synchronized before admission. The logger keeps at most 4 MiB including a reserved, explicit truncation footer, drains remaining input with a fixed 64 KiB buffer even after a disk/short-write error, and reports failure after draining. Exact-cap and empty streams are not truncated. A timeout wraps the entire producer/logger pipeline, including a child that keeps a pipe open. Either pipeline status failing retains pending state; an otherwise successful APT with a truncated log is not installation success. A timeout is not proof every child is quiescent.

### APT's duplicate terminal log

APT also copies terminal output into its own `term.log`; bounding the primary pipe alone is insufficient. The private configuration sets only `Dir::Log::Terminal "/dev/null"`. In [Debian APT 3.0.4 source](https://deb.debian.org/debian/pool/main/a/apt/apt_3.0.4.tar.xz), `pkgDPkgPM::OpenLog()` treats this exact path as an instruction not to open, chmod or write the duplicate terminal log. `DPkg::Use-Pty` alone does not establish that property. The primary merged logger remains enabled, including explicit truncation/error handling. APT history, dpkg action audit and other package-maintainer logs are not disabled or silently described as covered by this cap.

The separate `tests/apt-terminal-log.sh --disposable-dev-container` gate is opt-in and restricted to a disposable root DEV container using overlayfs. It installs a synthetic package producing more than 4 MiB, reproduces the uncapped duplicate, then checks the supported redirection removes only that duplicate while retaining bounded stdout/stderr, history and dpkg audit. This is not fresh-appliance or disk-exhaustion evidence. Remaining OS, history/planner and maintainer-script log growth needs its own storage policy and native qualification before a customer release.

## Failure limits

There is no generic repair/resume, automatic dependency rollback or marker-clearing operation. Unknown states preserve marker and evidence. Recovery requires proving all installation children stopped and verifying backups and live package/boot state through a separately reviewed procedure or the independently tested external recovery backup. A snapshot does not replace these checks. Pure tests do not prove real namespace isolation, native install behavior or power-loss durability. No such claim is made without separate evidence. No runtime daemons are added; installation resource measurements remain a native validation gate.
