# Preparación de migración offline

Mantén vivos el helper y el gestor de namespaces anteriores. Detén la API y su socket durante toda la ventana fría. `andeiva-preview grouped-inspect` crea un borrador inmutable sólo para root. Reanudar la API añade historia y deja obsoleta su huella. Respalda y retira expresamente sólo el borrador obsoleto conocido antes de inspeccionar de nuevo; los comandos nunca lo actualizan ni reparan automáticamente.

El instalador autorizado crea `/etc/andeiva-preview/grouped-migration-authorization.json` mediante O_EXCL, root:root 0600. JSON estricto: `{"version":1,"plan_sha256":"<digest exacto del borrador>","bindings":[{"source":"<origen FW>","actor":"<actor histórico explícito>","subject":"<nuevo sujeto durable explícito>","receipt_index":"<índice exacto de recibos FW>"}]}`. Cada vínculo concede continuidad de reintentos, no demuestra identidad humana histórica. No inferirlo del usuario ni de credenciales. El archivo de cuentas permanece intacto.

Ejecuta `andeiva-preview grouped-prepare` como instalador root sin reanudar la API entre inspección, autorización y preparación. Repite la inspección sin capacidades antes de provisionar. Un worker APIUID sin capacidades abre el FW original y nuevos directorios privados en `/var/lib/andeiva-preview/grouped`: `local-origin`, `state`, `admission`, `plan`, `emergency`. Rechaza y conserva directorios existentes o parciales. No cambia ni reclasifica ningún journal o directorio de arranque anterior.

El worker mantiene el bloqueo FW mientras cuatro callbacks acotados verifican realmente la política origen y la ausencia del dominio inactivo. El nuevo dominio local recibe exactamente un registro initialize con fecha actual. Ambos bloqueos de origen y el de destino permanecen durante el quinto callback y la publicación seleccionada. El padre root ejecuta observaciones state/kernel/state en el namespace anterior fijado; el worker no tiene privilegios ni comandos arbitrarios. Frames de hasta 64 KiB, secuencia y digest por solicitud, máximo cinco verificaciones. El límite de preparación de 180 segundos supervisa este proceso offline y no modifica los tres segundos de los efectos runtime.

`/etc/andeiva-preview/grouped-prepared.json` se publica con O_EXCL y sincronización. Contiene el hash exacto del borrador, procedencia local nueva, tres perfiles y presupuesto explícito 1 GiB/32768 inodos. Pools de 18 slots, capacidades admission/plan/emergency 4096/16384/8192 bytes. Raíces nuevas privadas API 0700/0600. **No activa el runtime**: faltan conversión del perfil compartido, persistencia de identidades con respaldo de cuentas, verificación completa independiente del helper, Boot y lectura del namespace nuevo, y cutover persistente antes de exponer el servicio. Fallos parciales o pérdida de ACK se conservan; no se reemplazan directorios para reintentar.

Las pruebas unitarias usan journals reales y lectura modelada explícitamente; verifican bloqueos, las dos reglas FW originales, procedencia local y fallos en cada callback. `TestRoutedMigrationPrepareNativeV3` exige `-andeiva-native-migration-prepare-v3`, binario confiable propiedad de root, ventana fría recién autorizada y destinos vacíos. Crea almacenamiento preparado sin activar runtime. Su omisión predeterminada no constituye evidencia.
