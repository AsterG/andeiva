# Preparação de migração offline

Mantenha vivos o helper e o gerenciador de namespaces antigos. Pare a API e seu socket durante toda a janela fria. `andeiva-preview grouped-inspect` cria um rascunho imutável somente para root. Reiniciar a API acrescenta histórico e torna a impressão obsoleta. Faça backup e retire explicitamente somente o rascunho obsoleto conhecido antes de nova inspeção; os comandos nunca atualizam ou reparam o arquivo automaticamente.

O instalador autorizado cria `/etc/andeiva-preview/grouped-migration-authorization.json` usando O_EXCL, root:root 0600. JSON estrito: `{"version":1,"plan_sha256":"<digest exato do rascunho>","bindings":[{"source":"<origem FW>","actor":"<ator histórico explícito>","subject":"<novo sujeito durável explícito>","receipt_index":"<índice exato dos recibos FW>"}]}`. Cada vínculo concede continuidade de repetição, não comprova identidade humana histórica. Nunca inferir por nome ou credencial. O arquivo de contas permanece intacto.

Execute `andeiva-preview grouped-prepare` como instalador root, sem reiniciar a API entre inspeção, autorização e preparação. A inspeção sem capacidades é repetida antes do provisionamento. Um worker APIUID sem capacidades abre o FW original e diretórios novos privados em `/var/lib/andeiva-preview/grouped`: `local-origin`, `state`, `admission`, `plan`, `emergency`. Diretórios existentes ou parciais são recusados e preservados. Nenhum journal ou diretório de boot anterior é alterado ou reclassificado.

O worker mantém o bloqueio FW durante quatro callbacks limitados que verificam realmente a política original e a ausência do domínio inativo. O domínio local recebe exatamente um registro initialize com data atual. Os dois bloqueios de origem e o de destino permanecem durante o quinto callback e a publicação selecionada. O pai root executa observações state/kernel/state no namespace antigo fixado; o worker não tem privilégios ou comandos arbitrários. Frames de até 64 KiB, sequência e digest por solicitação, máximo cinco verificações. O limite de 180 segundos supervisiona a preparação offline e não altera os três segundos dos efeitos runtime.

`/etc/andeiva-preview/grouped-prepared.json` é publicado com O_EXCL e sincronização. Contém hash exato do rascunho, proveniência local nova, três perfis e orçamento explícito de 1 GiB/32768 inodes. Pools com 18 slots e capacidades admission/plan/emergency 4096/16384/8192 bytes. Raízes novas privadas API 0700/0600. **Não ativa o runtime**: conversão do perfil compartilhado, persistência das identidades com backup das contas, verificação completa independente pelo helper, Boot e leitura do namespace novo e cutover persistente são necessários antes da exposição. Falhas parciais ou perda de ACK são preservadas; não substituir diretórios para repetir.

Testes unitários usam journals reais e leitura modelada explicitamente; verificam bloqueios, duas regras FW originais, proveniência local e falhas em cada callback. `TestRoutedMigrationPrepareNativeV3` exige `-andeiva-native-migration-prepare-v3`, binário confiável pertencente a root, janela fria recém-autorizada e destinos vazios. Cria armazenamento preparado sem ativar runtime. O skip padrão não é evidência.
