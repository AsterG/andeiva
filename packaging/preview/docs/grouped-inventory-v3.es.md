# Inventario de red desde el helper

Las factories del appliance compuesto negocian expresamente `routed_inventory.v1` como quinta característica IPC3, después de las tres originales y `routed_integrity_gate.v1`. Los perfiles anteriores de tres o cuatro características siguen disponibles en sus factories confiables. La API de producción exige cinco y rechaza un helper anterior antes de abrir el escritor; nunca descubre interfaces en el namespace host de la API como alternativa.

La solicitud `inventory` contiene un objeto vacío. No selecciona namespace, interfaz, ruta ni comando. El proveedor helper verifica el namespace del proceso y del hilo actual contra metadata confiable del gateway antes y después de `networkinventory.Discover`. Se realizan dos observaciones completas y se rechazan cambios detectables. Las llamadas al sistema de la biblioteca estándar no admiten cancelación individual por contexto. El inventario no crea política, enlaces, direcciones, rutas, timers ni listeners.

Se validan campos tipados explícitos y claves anidadas obligatorias en ambos extremos. Se conservan internamente direcciones host IPv4/IPv6, máscaras anulables y zonas separadas. Observaciones inválidas, incompletas, con escalares nulos, duplicadas o demasiado grandes fallan completas; no se sustituyen por caché, éxito vacío ni datos del host. El presupuesto conservador de JSON escapado es 256 KiB, además de los límites existentes de interfaces y direcciones. Un appliance mayor puede devolver no disponible en vez de un resultado parcial.

La API sin capacidades recibe datos sólo mediante el canal heredado autenticado del helper, con run, namespace, secuencia monotónica y plazo de tres segundos existentes. Conecta ese proveedor al endpoint autenticado `/api/v2/network/interfaces`. Conserva RBAC y filtrado del DTO público: ifindex, flags punto-a-punto/multicast y zonas internas no se añaden a diagnósticos públicos. TLS de administración y SO_NETNS_COOKIE siguen validándose en el namespace host.

El inventario no califica integridad, renueva leases ni declara Ready. Un fallo no elimina el último ruleset válido. Las pruebas cubren tipos, límites, solicitud sin argumentos, negociación, rechazo de downgrade, lecturas nuevas, errores y rechazo de descubrimiento del host API. Los fixtures de transporte son observaciones modeladas dentro del proceso; el descubrimiento desplegado del gateway y la instalación completa requieren evidencia nativa separada.
