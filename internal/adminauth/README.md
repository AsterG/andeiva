# Administrative login admission

Experimental scope: provisioned random credentials in the isolated administration
preview. [Español](docs/es.md) · [Português](docs/pt.md).

Network transports call `LoginFrom` with the receiving socket's IP address. HTTP
uses `RemoteAddr`; SSH uses connection metadata. Forwarding headers are ignored.
IPv4-mapped IPv6 is normalized; missing, malformed, scoped, unspecified or multicast
peers are rejected. Reverse-proxy origin delegation is not implemented.

Anonymous failures share a process-wide allowance of four admitted attempts per
second and a per-origin allowance. The fixed table holds 128 origins with lazy
one-minute retention; rejected attempts do not extend retention or evict active
entries. Verified credentials use a separate four-per-second allowance and bypass
the anonymous origin table, including when full or behind the same NAT. Existing
32-session, expiry, CSRF, RBAC and required-audit checks remain in force. The legacy
internal `Login` entry point shares the anonymous allowance for every attempt.
If its credentials are valid, it also consumes the process-wide verified
allowance; invalid credentials never consume that allowance. This prevents
internal callers from creating an extra verified-login budget. Production HTTP
and SSH credential transports use `LoginFrom`, not this compatibility entry point.

Classification before admission is bounded to a 64-byte username and a 64-character
credential. These credentials contain 32 randomly generated bytes; this mechanism
must not be reused as password hashing for user-chosen passwords. No credential,
cookie or source-controlled secret is added to audit records.

Admission is process-local and resets on restart. It limits admitted failures, not
all network handshakes or CPU consumption. SSH's existing borrowed HTTPS-session
authentication path is unchanged. This does not protect every possible denial of
service or make an exhausted audit store recoverable. Required audit failure still
closes authentication. There is no new retention, aggregation, audit deletion,
persistence format, background worker or forwarding-policy change.

## Reproduction

With the repository's Go toolchain and dependencies available:

```sh
go test -race -count=1 ./internal/adminauth ./internal/adminapi ./internal/localssh
go vet ./cmd/... ./internal/...
go build ./cmd/... ./internal/...
# Linux: actual loopback TCP sockets and verified server TLS; no root required.
go test -race -count=10 ./internal/adminapi -run '^TestLoginOriginFloodCannotBlockVerifiedHTTPS$'
```

Deterministic manager tests cover exact quotas, flood admission, table capacity,
expiry, clock rollback, IPv4/IPv6, shared NAT, concurrency, sessions and audit failure.
HTTP tests reject forged forwarding headers and check the same Web/CLI/API behavior.
SSH tests exercise real transport and invalid peer metadata. The Linux HTTPS test
uses `127.0.0.2/3` as source addresses, a trusted test-server certificate and a bounded
client timeout. Invalid requests may return 401 or 429 across real clock windows;
the exact allowance is asserted with a controlled clock in manager tests. Backend
configuration and audit sinks in these tests are fixtures; no nftables traffic or
installed appliance state is changed.

The admission state measures 7,232 bytes on the tested Linux AMD64 build. This is
the fixed structure size, not process RSS or a throughput guarantee. Microbenchmarks
exclude transport and durable audit I/O. Full-volume audit recovery remains a
separate release blocker.
