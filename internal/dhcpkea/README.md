# DHCP configuration compiler for Kea 2.6.3

Status: deterministic compiler only. No process, listener, lease file, service
unit, API, configuration store or network change is created. The engine profile
requires native qualification before enablement. [Español](docs/es.md) ·
[Português](docs/pt.md).

`Compile(dhcpserver.Config, []Binding)` reuses schema 1 validation. Assembly must
provide exactly one binding per retained scope: selected static LAN address,
kernel interface name and stable `SubnetID`. Bindings are operational inputs,
excluded from JSON; validation is not proof of live interface ownership.
Duplicate names/IDs, missing/extra bindings, WAN, IPv6, wildcard/interface-address
selectors and malformed configuration are rejected with
`ANDEIVA_DHCP_KEA_INVALID`. Subnet IDs range from 1 through 4294967294.

The future assembly **must preserve the scope-to-SubnetID association across
configuration changes and restarts**. Never derive it from array position,
truncate a hash, reuse an old identity blindly or introduce a second configuration
database. This compiler supplies no allocator/history or lease-continuity proof.

Disabled configuration is still validated, including retained scopes, then returns
an empty artifact (`Enabled=false`, `JSON=nil`, empty digest). The caller must drain
existing resources to claim disabled; an empty artifact is not that observation.

Enabled output has explicit LAN RAW interfaces with require-all and no socket
retry. It includes fixed lease/T1/T2 values, gateway, ordered DNS/NTP options and
optional domain. Pools are numerically ordered and split around excluded/reserved
addresses. MAC reservations are out of the resulting dynamic pools; even a pool
emptied by exclusions stays empty. Reservations are allocation preferences, not
device authentication. Normal DHCP client-ID lease matching remains enabled;
administrative client-ID reservations are unsupported.

Each subnet additionally requires a fixed class matching its trusted ingress interface, including address-based renewal selection. The fixed DROP class rejects relayed giaddr/option82 traffic. No DDNS, hooks,
control socket, database credentials, arbitrary options, caller paths/executables
or DHCP4-over-DHCP6 setting is generated. The compiler creates no nftables rule;
RAW isolation, mandatory resource identification, local policy and unknown-traffic
handling remain runtime requirements. There is no forwarding/NAT permission.

Operational memfile data uses only `/var/lib/andeiva/dhcp-server/leases4.csv`, with
persistence requested and hourly lease-file cleanup. It must never be restored
from a configuration revision during rollback. The caller must provision owned
storage, confine the engine/LFC helper, preserve lease ownership and enforce
disk/inode limits. No crash, disk-full, restart, power-loss or migration guarantee
is made here.

Kea 2.6.3's `max-row-errors=0` allows unlimited corrupt rows. The compiler sets the
smallest positive value, 1; source `lease_file_loader.h` still permits one skipped
row before failing on the second. `sanity-checks.lease-checks=warn` prevents automatic
repair/deletion but does not prove valid historical leases. **Runtime must refuse
unproven/corrupt lease state before serving**; a clean `-t` result cannot establish
that. No custom DHCP or CSV recovery parser is introduced.

Limits remain 32 scopes, 32 declared pools per scope, 256 exclusions and 256
reservations per scope, 65,536 declared dynamic addresses total, and 64 KiB encoded
input. Interval splitting does not enumerate entire networks. Output is bounded
to 1 MiB. Single threading, disabled receive queue and one statistic sample bound
some engine settings; they are not throughput/resource qualifications. Logs go to
stdout at WARN; lifecycle/audit and log retention belong to runtime assembly.

The artifact digest is SHA256 of generated bytes, not a selected revision or
authorization. Scope/pool/exclusion/reservation/binding reordering is deterministic;
DNS/NTP preference order is deliberately preserved. Inputs are not mutated.

## Reproduce

```sh
go test -race ./internal/dhcpkea
go vet ./internal/dhcpkea
go test -run='^$' -bench=Compile -benchmem ./internal/dhcpkea
GOOS=windows GOARCH=amd64 go build ./internal/dhcpkea
```

`testdata/kea-2.6.3.json` is generated by the tested synthetic LAN fixture and
checked byte-for-byte. An authorized isolated laboratory may pass it to the
verified Kea 2.6.3 binary with `-t`; this checks configuration, not runtime or
persistence. The compiler does not invoke that executable.

One Linux/WSL development run: race 1.091 s; small compile 9,991 ns/op,
4,593 B/op; dense two-scope compile 768,860 ns/op, 450,129 B/op. Three dense scopes
produce 100,897 bytes from 49,321 input bytes; four exceed the input bound and
are rejected. These are compiler measurements, not appliance/server benchmarks.
No Docker/EKS runtime is introduced. Native packet/lifecycle/resource tests remain pending. The pure compiler was
independently reviewed; that review does not qualify service execution.

Lease caching options are omitted: Kea 2.6.3 requires explicit configuration to
enable caching. Its parser rejects a configured zero threshold. A regression
checks that neither `cache-threshold` nor `cache-max-age` is emitted. This default
is not a lease durability guarantee; the resulting fixture passed Kea 2.6.3 native parsing with the stock AppArmor
profile retained. Parsing does not start or qualify a DHCP service. See the engine's
[lease caching documentation](https://kea.readthedocs.io/en/kea-2.6.3/arm/dhcp4-srv.html#lease-caching),
`BaseNetworkParser::parseCacheParams` and `AllocEngine::setLeaseReusable`.

Engine references: [DHCPv4 configuration](https://kea.readthedocs.io/en/kea-2.6.3/arm/dhcp4-srv.html)
and [classification](https://kea.readthedocs.io/en/kea-2.6.3/arm/classify.html).
Exact source consulted: `isc-kea` 2.6.3, `lease_file_loader.h` and DHCPv4 parser.
